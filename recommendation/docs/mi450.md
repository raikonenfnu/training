# Bring-up on MI450 A0 (gfx1250, single GPU)

Running the yambda-5b HSTU ranker on an **MI450 A0 engineering sample**. The
stack works — fbgemm builds, TorchRec shards, the 4.76B-event dataset streams,
the benchmark reaches `run_stop` — but **training does not survive**: the loss
goes `nan`. Best known configuration trains correctly for ~2150 steps (~12 min),
loss decreasing and matching the PyTorch reference, then poisons:

```bash
IMG=recommendation-amdprimus0815:triton-3.7.1-amd   # Triton 3.7.1, AMD build
AMDGCN_USE_BUFFER_OPS=0                             # default in the runner
./scripts/run_smoke_shrink_1gpu.sh
```

### Images tested

All four repo images are the same [`Dockerfile.amdprimus0815`](../Dockerfile.amdprimus0815)
build — same torch `2.11.0+rocm7.14.0a20260625`, same ROCm, same fbgemm and
torchrec — with **only the Triton wheel swapped** (`--no-deps`). So Triton is the
only variable across them. Select one with `IMG=`; the runner defaults to the
3.6.0 image.

- **`recommendation-amdprimus0815:gfx1250`** — Triton `3.6.0+rocm7.14.0` (AMD SDK,
  as shipped in the base image). Runner default. `nan` by step 50.
- **`recommendation-amdprimus0815:triton-3.7.1-amd`** — Triton
  `3.7.1+git0263a6a6.rocm7.14.0`. **Best known**: trains to step 2150.
- **`recommendation-amdprimus0815:triton-3.8.0-amd`** — Triton
  `3.8.0+git4cff872c.rocm7.14.0`. Memory access fault at `gstep=0`. One root
  cause is isolated and fixed (defect 4) but at least one more remains, so this
  image is still unusable.
- **`recommendation-amdprimus0815:triton-main`** — Triton built from `main` @
  `58895270`. Will not compile the kernels *without* the pointer port ([5]).
  (Built via
  [`scripts/build_triton_from_source.sh`](../scripts/build_triton_from_source.sh);
  note `docker commit` of a `sleep`-kept container inherits that `ENTRYPOINT`, so
  this tag resets it back to `bash`.)
- **Current main under test:** `triton-lang/triton` @
  [`7ff97e3109`](https://github.com/triton-lang/triton/commit/7ff97e310935b4a79794878dbc911f9af25d38d9)
  (Triton reports `3.8.0`), layered on `:gfx1250` with the same build script
  (`TRITON_COMMIT=7ff97e310935b4a79794878dbc911f9af25d38d9`). Compiles after the
  pointer port; e2e still dies mid-run in `_hstu_attn_bwd` ([6]).

Base images, for reference: `amdprimus/amdprimus:0815` is what the repo image is
built `FROM`, and `amdprimus/amdprimus:gfx1250-20260831` was evaluated and
rejected — its `libtriton.so` is byte-identical to `:0815`, so a newer image is
not a newer Triton.

Branch `chcai/mi450_a0`. Companion to [`training_recipe.md`](./training_recipe.md)
and [`perf_opt.md`](./perf_opt.md).

## Everything known about the open problems

All are in the Triton path; none is in the benchmark's math. The table is
**ordered by Triton version, oldest first**, so it answers "what breaks on the
version I am about to run". Only the Triton wheel was ever swapped (`--no-deps`),
holding torch, ROCm and driver constant, so Triton is the only variable.

The reproducer is split into two columns by what it costs to run: **e2e** needs
the prepared yambda-5b cache and a training run, while **standalone** covers
everything runnable without a dataset — the `scripts/repro_gfx1250_*.py`
scripts, the unit tests, and the compile-only checks. Both cells are always
filled, so a "none" is stated rather than left to inference; some defects have no
standalone reproducer at all, which is most of what makes them expensive.

A defect that spans versions is listed once, with every version it was tested on
in the version column. The `#` column is only row position and renumbers whenever
the table is re-sorted, so **cite a defect by its bracketed id, not by row
number** — row 6 is defect [4]. **Tested** is a recording date, not an id. Those ids are stable and are referenced from code
comments in `common.py`, `ops/utils.py` and `dlrm_v4/train/utils.py`, so keep them
if you re-cut this table. Defects 1 and 2 are ready to hand to the Triton team
as-is, defect 3 is the blocker on the version we ship, and defect 4d is what
stops AMD 3.8.0, and defect 6 is what is left on current upstream `main`.

### Running the reproducers

Every reproducer runs in one of the four repo images, which differ only in the
Triton wheel — pick one with `IMG=`. `repro_gfx1250_buffer_ops.py` and `repro_gfx1250_pipeliner.py`
need **only torch and Triton** (no repo imports, no fbgemm, no dataset), so those
are the ones to hand over without this tree. `repro_gfx1250_fused_rng.py`,
`repro_gfx1250_attn_bwd.py` and `repro_gfx1250_latest_main.py` import the HSTU
kernels and need the repo on `PYTHONPATH`.

```bash
IMG=recommendation-amdprimus0815:triton-3.8.0-amd  # or :gfx1250, :triton-3.7.1-amd, :triton-main
docker run --rm -it \
  --device=/dev/kfd --device=/dev/dri \
  --group-add "$(getent group video | cut -d: -f3)" \
  --group-add "$(getent group render | cut -d: -f3)" \
  --ipc=host --security-opt seccomp=unconfined --shm-size=64g \
  -v "$PWD:/workspace/recommendation" -w /workspace/recommendation \
  -e PYTHONPATH=/workspace/recommendation \
  -e AMDGCN_USE_BUFFER_OPS=0 \
  -e HSA_COREDUMP_PATTERN=/tmp/gpucore.%p.gpu \
  "$IMG" <the command from either reproducer column>
```

- **A hang costs a reboot** plus `sudo modprobe amdgpu` afterwards, since `amdgpu`
  is blacklisted on the kernel cmdline. A memory-access *fault* is recoverable —
  the process dies and the GPU comes back. So leave the hang reproducers for last,
  and run **one test per process under a hard timeout**: `pytest` orders
  `unittest` methods alphabetically, so a sweep that wedges blames the wrong test.
- **To name the faulting kernel, set `AMD_SERIALIZE_KERNEL=3`.** It makes the
  async fault synchronous and prints `kernel: <name>`; without it you get only an
  address, and a queue wedged behind the fault looks exactly like a hang.
  `AMD_LOG_LEVEL=3` filtered to `ShaderName` gives the last dispatch before it.
- **A fault writes a coredump the size of allocated VRAM** (9–36 GB observed).
  `HSA_ENABLE_COREDUMP=0` does *not* suppress it on this runtime, so keep
  `HSA_COREDUMP_PATTERN` pointed out of the working tree.
- **Unit tests** need `import fbgemm_gpu` before `pytest` collects, and
  `pip install hypothesis`. In `hstu_attention_test.py`, `test_attn` is a helper
  that `pytest` mis-collects, so name the class test explicitly.
- **E2e reproducers** need the prepared yambda-5b cache under `DLRM_DATA_PATH` and
  go through [`scripts/run_smoke_shrink_1gpu.sh`](../scripts/run_smoke_shrink_1gpu.sh),
  which defaults `AMDGCN_USE_BUFFER_OPS=0` and forwards `IMG`,
  `NUM_TRAIN_BATCHES`, `PROGRESS_EVERY`, `AMD_SERIALIZE_KERNEL`,
  `TRITON_ALLOW_PIPELINING` and `DEBUG_NAN_HOOKS`. Check `ps -eo pid,cmd | grep train_ranker` first — an
  interrupted run can outlive its shell, and two trainings sharing the GPU
  invalidates the result.

**Tested** is the UTC calendar day the result in that row was recorded
(the latest confirmatory run, if it was re-run).

### Row 7 follow-up: coexec scheduler root cause

The standalone [`repro_gfx1250_fused_rng.py`](../scripts/repro_gfx1250_fused_rng.py)
reproduces row 7 directly at the recorded `N=18187`, `D=512`, bf16 launch.  It
also checks the gradients, recomputed output, and all three dropout masks, which
exposed silent corruption at four warps in addition to the two-warp fault.

The proximate compiler root cause is the gfx1250 **coexec machine schedule under
LLVM expert-scheduling mode**, enabled by ROCm/triton commit
[`89db5e470c`](https://github.com/ROCm/triton/commit/89db5e470c330ea6f51ea3763a5dda58083f780c).
That commit is an ancestor of `4cff872c`, but is absent from the passing AMD
3.7.1 commit `0263a6a6`.  Holding the source, LLVM, input, two-warp launch, and
all other options fixed gives this matrix:

| coexec attribute | expert mode | result | backward VGPRs |
|---|---|---|---:|
| on | on | memory-aperture fault | 254 |
| off | on | correct | 135 |
| on | off | correct | 254 |

The last two rows separate the scheduler defect from register pressure alone.
With both controls enabled, two warps fault and four warps silently corrupt
results; eight warps is correct because Triton does not request coexec above
four warps.  Disabling coexec fixes the two- and four-warp kernels, including
`FAST_DROPOUT=True` and `COMPUTE_Y=False`.

For an unmodified `3.8.0+git4cff872c`, the immediately available compiler
workaround is:

```bash
AMDGCN_USE_BUFFER_OPS=0 TRITON_HIP_USE_EXPERT_SCHEDULING=0 \
  python scripts/repro_gfx1250_fused_rng.py
```

A narrower compiler workaround is to backport ROCm/triton
[`#11272`](https://github.com/ROCm/triton/pull/11272), then run with
`TRITON_HIP_USE_COEXEC_SCHEDULER=0`.  The backport adds a cache-invalidating
knob so toggling the scheduler cannot reuse an incompatible cached binary.  The
existing separated-RNG application workaround remains preferable when only
this operation needs protection; `num_warps=8` is another verified but
performance-untuned kernel workaround.  The recommended image already contains
the proposed ROCm 7.14 / torch 2.11 gfx1250 nightly stack, so reinstalling those
wheels does not address this compiler-scheduling defect.

built from source with bundled LLVM `b010a18d`, passes the original two-warp

pair is correct in lanes 1--31 and corrupt only in lane 0, in every stopped
wave. In the reduced kernel lane 0 is displaced by exactly `0x6d0c6e1a`; the
producer multiplies the long-lived V-lane offset by two, so its corrupt input
is `0x3686370d` -- plausible FP32 accumulator data -- instead of integer zero.
In the full kernel the same input is physical **v257** and the same first store
faults even with coexec disabled. Later address fragments derived from the
offset before the WMMA region remain correct. The bad value is therefore a
live-VGPR overwrite, not bad `seq_offsets`, pointer arithmetic, scratch
addressing, or an asynchronous report from a different instruction.

The physical allocation explains why the fault needs this large tile. The
lane offset is allocated to **v257**, whose low eight-bit encoding aliases v1
and is selected through gfx1250's mutable `s_set_vgpr_msb` state; it stays live
across the WMMA-heavy body. Recomputing only this offset after the final WMMA
region (leaving the math, masks, pointers, launch and coexec schedule otherwise
unchanged) moves it to a short-lived low VGPR and survives 4000 iterations.
The original reduced binary with the same seed faults. Disabling only
`amdgpu-sched-strategy=coexec` survives 7000 reduced iterations on LLVM
`b010a18d` and 4000 on `ce352942`; disabling expert mode while retaining the
coexec attribute still faults. Coexec is therefore causal for the reduced
kernel, but it is **not a complete workaround** for the full specialization.

Matched full-kernel stress runs make that distinction explicit. With coexec
off, seed 1234 survives 4000 iterations on both LLVM `b010a18d` and
`ce352942`. The same cached `ce352942` binary faults at step 0 in a seed-4321
run and at the first final-DV store under precise-memory replay; a one-iteration
replay can also pass, confirming a placement/timing-sensitive hazard rather
than a deterministic bad address expression. Forcing `waves_per_eu=2` caps the
full kernel at 512 VGPRs while increasing scratch from 412 to **2372 bytes**;
with coexec off it survives 1000 seed-4321 and 4000 seed-1234 iterations.
Conversely, enabling coexec on that 512-VGPR form still faults after step 100
in an uninstrumented run (the debug agent perturbs it enough to survive 1000).
More spilling can therefore pass, and fewer VGPRs can still fault: **spill
traffic is not the root cause**. Coexec scheduling and the 1024-VGPR
extended-register allocation are two trigger surfaces for the same lane-0
live-register corruption.

The compiler-stage boundary is exact. Matching both cached kernel
specializations from the `ce352942` coexec-on and coexec-off runs shows
byte-identical TTIR and TTGIR. Their LLIR is also byte-identical after deleting
the sole `"amdgpu-sched-strategy"="coexec"` function attribute; the address
arithmetic and stores do not otherwise change. AMDGCN is the first materially
different representation (962 versus 960 VGPRs, both with zero scratch), and
the runtime result follows that machine code. Therefore the Triton kernel,
TTIR/TTGIR lowering, and LLVM-IR address expression are not the defect. The
LLIR attribute is the trigger in that reduced comparison, but the failing
transformation is in LLVM's LLIR-to-AMDGPU machine
scheduling/register-allocation path (or an A0 hardware hazard that this path
must model). The `global_store_b128` is only where the already-corrupted
address becomes observable; it is not itself mis-lowered.

LLVM [`85c730242e`](https://github.com/llvm/llvm-project/commit/85c730242e741f79bf7ca543bdf496dfb89a7f22)
adds a gfx1250 pre-RA model for WMMA's nine-cycle `0EIIEEIIV` co-execution
window. Triton's consumed `llvm-info.json` pin, `b010a18d` (not the newer
`llvm-build-info.json` value), predates that change. However, rebuilding the
same Triton source against post-fix LLVM `ce352942` does **not** fix this
kernel: the unmodified reduced repro still faults at step 0, with 962 VGPRs and
zero scratch. The earlier `s_nop 7` result is **retracted as a fix**: an
identical 4000-iteration repeat faults at step 0. `s_nop 0` or `s_nop 7` on
either side of every `s_set_vgpr_msb`, eight `v_nop`s after every WMMA, and
`s_wait_alu` drains for either `depctr_va_vdst(0)` or `depctr_vm_vsrc(0)` also
fault at step 0. The first passing padding run was a Heisenbug, not proof of a
fixed WMMA spacing.

Two independent compiler controls now identify the durable condition. First,
recomputing the lane offset after the final WMMA survives 4000 iterations in
two clean LLIR replays, so the original long-lived v257 is the corrupted state.
Second, compiling the **identical original LLIR** with
`-mattr=-1024-addressable-vgprs` removes every `s_set_vgpr_msb`, limits the
kernel to 256 VGPRs (2468 bytes scratch), and survives 4000 seed-4321
iterations; the extended-VGPR build faults at step 0. The root cause is thus a
gfx1250-A0 extended-VGPR live-value/selection failure across the WMMA region,
not a particular padding distance. LLVM's AMDGPU allocation and late
`AMDGPULowerVGPREncoding` pass create the hazardous form, while the hardware
may be the component that violates its intended preservation semantics. The
correct LLVM resolution is an A0-gated erratum mitigation: avoid carrying
cheap address-critical work-item values in extended VGPRs across WMMA, or
conservatively disable 1024-addressable VGPRs. Native B0 validation is required
before choosing the stepping gate. Coexec makes the failure easier to hit, but
the full 1024-VGPR form also faults with coexec off. Buffer addressing is not
on this path (`AMDGCN_USE_BUFFER_OPS=0`) and is a separate issue.

The current gfx1250 workaround uses `BLOCK_N=64` for Triton 3.8 and newer. It
reduces the full specialization to 758 VGPRs without scratch. Both the reduced
and full repros survive 4000 iterations, and all eight deterministic BF16
`attn_check.py` forward/backward cases pass at their original tolerances. The
same default passes on upstream `7ff97e3109` and AMD
`3.8.0+git4cff872c`; other AMD architectures and older Triton versions retain
the existing `BLOCK_N=128` pin. Use `--bw-config` to restore the failing tile or
sweep alternatives without editing the kernel, for example:

```bash
AMDGCN_USE_BUFFER_OPS=0 AMD_SERIALIZE_KERNEL=3 \
  python scripts/repro_gfx1250_attn_bwd.py --part bwd --layout contiguous \
  --contextual 0 --no-targets \
  --bw-config m=32,n=128,warps=4,stages=1,nonkdim=16,waves=0
```

The workaround also passes the row-10 e2e acceptance run on upstream
`7ff97e3109`: `EMBEDDING_ROW_SCALE=0.25`, batch size 8, 4000 training batches,
two evaluation batches, `AMD_SERIALIZE_KERNEL=3`, and
`AMDGCN_USE_BUFFER_OPS=0`. It exits 0 after all 32,000 training samples, reports
finite `train_loss=0.09993` at step 4000, completes both evaluations, and emits
`run_stop`; the complete log contains no HSA fault, traceback, NaN, or infinity.
The production-mode repeat with `AMD_SERIALIZE_KERNEL` unset also exits 0 after
4000 batches and `run_stop`, with finite final `train_loss=0.09992`. Its
training elapsed time is 311.6 seconds versus 449.7 seconds for the serialized
run, but that is not a controlled performance comparison because the second
run reused the Triton compiler cache.
The cached TTIR encodes `BLOCK_M=32, BLOCK_N=64`, and the e2e specialization's
assembly uses 654 VGPRs with zero private scratch. `run_stop` says `aborted`
because this bounded smoke deliberately sets the unreachable
`AUC_THRESHOLD=1.0`, not because execution failed.

Keep `AMDGCN_USE_BUFFER_OPS=0`; the independent buffer-addressing hang has not
been cleared on latest main. The existing descriptor/TLX path is NVIDIA
Hopper-specific and deliberately disabled on HIP.

## The node

1× MI450 A0 engineering sample, `gfx1250`, PCI `1002:75c1`, SKU `M4500001`, rev
`0x00` — 256 WGPs, ~432 GiB HBM, **`warp_size=32`** (RDNA, not CDNA wave64).
ROCm 7.14, torch `2.11.0+rocm7.14.0a20260625`, Triton 3.6.0 stock. Host Linux
`6.14.0-37-generic`, amdgpu DKMS 7.1.1, Docker 29.6.1.

Two facts drive every change here: **one GPU** (the whole model must fit in one
HBM) and **wave32** (CDNA assumptions in fbgemm are wrong).

`amdgpu` is blacklisted by the kernel cmdline
(`modprobe.blacklist=amdgpu,device_dax,dax_hmem`), so after every boot run
`sudo modprobe amdgpu` — `/dev/kfd` appears ~15 s later.

**Recovery from a hang is a reboot.** The process sticks in uninterruptible `D`
state, `docker kill` returns *"did not receive an exit event"*, MODE2 reset fails
with `error code -62`, and `modprobe -r amdgpu` deadlocks. The wedge is
whole-device and survives container teardown: `rocm-smi` still answers while
holding VRAM with no processes alive, and a bare 1024² bf16 matmul in a fresh
container never returns. Untried: `flr`/`bus` reset and the `umr` wave debugger.

## Getting it to run

**Image** — [`Dockerfile.amdprimus0815`](../Dockerfile.amdprimus0815). Stock
`rocm/primus:v26.3` torch has no gfx1250 code objects, so *any* kernel fails with
`CUDA error: device kernel image is invalid`. `amdprimus/amdprimus:0815` has
gfx1250 torch but no fbgemm/torchrec, so those are built on top (~8 min). ROCm
lives in the wheel at `site-packages/_rocm_sdk_devel`, not `/opt/rocm`, so
`ROCM_HOME`/`HIP_ROOT_DIR` must point there or configure dies with
`BUILD_ROCM_VERSION is not set`. Also needs `libtbb-dev`, `libnuma-dev`,
`libssl-dev`, `ninja-build`.

**Three fbgemm patches** — (1) `Fbgemm.cmake` omits `FbgemmFloat16Convert*.cc` /
`FbgemmBfloat16Convert*.cc`, relying on torch's bundled FBGEMM; (2) host/device
**warp-size disagreement**, host assumed wave64; (3) codegen also hardcodes
wave64. With these, TBE is **bit-exact** against CPU.

**Embedding shrink** — `EMBEDDING_ROW_SCALE`; the reference tables are ~559 GiB
of fp32 weights against one ~432 GiB GPU.

**Dataset** — use the **MLCommons prepared download** (README Option A): 227.41
GB, 19 files, all md5/sha256 verified. Do **not** self-preprocess; the cache build
needs ~190 GB RAM and OOM-killed this 251 GB box.

## Performance

Triton 3.7.1, gin-default depth 3, `MAX_SEQ_LEN=4096`, `EMBEDDING_ROW_SCALE=0.25`,
`BATCH_SIZE=128`, buffer ops off — measured in the finite region, while the loss
was still converging. Step 50 is warmup (1920 ms, carrying compile and autotune).
Steady state is **~322 ms/step, ~395 samples/s, `tflops_real` 35–61, HFU
1.1–1.9%**. HFU tracks `fill` (29–49%) rather than being a fixed number, because
`fill` is the fraction of the dense-equivalent work the jagged batch actually
contains.

**Read `hfu`, not `mfu`.** `num_flops_per_sample` is a *static dense* estimate
(315.7 GFLOP/sample at 3 layers) while jagged attention performs only the `fill`
fraction of it, so `mfu` (3.7–4.2%) describes work that is never executed.
`tflops_real` is the honest count and `hfu` its utilization.

HFU is against **3150 TFLOP/s = 90% of the 3500 TFLOPS dense BF16 matrix peak**
for MI450. Two notes on that denominator. `get_gpu_peak_flops` matched nothing and
silently fell back to **MI350X's 2300 TFLOPS**, because these parts report the
generic name `AMD Radeon Graphics`, so every earlier perf line in this repo's logs
is normalized against the wrong chip; it is now keyed on `gcnArchName`. And the
silicon peak is used deliberately, not the ~75 TFLOP/s (~2% of it) this node can
actually reach today: measured bf16 GEMM is only **1.46× fp32** (67.8 vs 46.5 TF
at N=8192), i.e. the **matrix cores are idle** and everything runs on the vector
path at ~1.1 GHz against a 2.4 GHz max clock. Normalizing against measured
throughput would conflate model efficiency with BLAS immaturity and would
silently change meaning as kernels improve.

## Retracted

`and`/`or` on tensors is **not** a bug, and the `triton_position.py` rewrite was
cosmetic. Triton warns `Logical operators 'and' and 'or' are deprecated for
non-scalar tensors`, but `code_generator.py:visit_BoolOp` (3.6.0) lowers them to
`logical_and`/`logical_or`, which for boolean masks is exactly `&`/`|`. Nothing
goes unmasked. The position test passing afterwards was nondeterminism.

Separately, `hstu_compute::test_compute_output` was an **inherited code bug, not a
GPU bug**: the forward dropped `mul_u_activation_type`, so it applied no
activation while its own backward applied one. A one-line fix takes that parameter
grid from 32 mismatches to 0. Our file is byte-identical to
`mlcommons/training@master`, and the defect is dormant in the benchmark, which
only ever passes `"none"`.
